<summary><h1>Nov 23rd, 2026</h1></summary>

#### Goal: join the Windows client VM to lab.local

### 7:40 PM

Built the client VM. Windows 11 eval ISO, 4GB RAM, NAT network, same VMnet as the DC.

Set a static IP the same way as DC01, just a different address on the subnet:

```
New-NetIPAddress -InterfaceAlias "Ethernet0" -IPAddress 192.168.174.20 -PrefixLength 24 -DefaultGateway 192.168.174.2
Set-DnsClientServerAddress -InterfaceAlias "Ethernet0" -ServerAddresses 192.168.174.10
```

Important difference from the DC: DNS points at DC01's IP (192.168.174.10), not 127.0.0.1. A client resolves through the DC, it doesn't try to be its own DNS server.

Tested with `Resolve-DnsName lab.local` and got a timeout.

Spent a minute thinking the static IP or DNS config was wrong again. It wasn't. DC01 was just powered off. No DC running means nothing is listening on 192.168.174.10 to answer the query. Turned DC01 on, ran the same command again, resolved fine.

Lesson: check the DC VM is actually running before troubleshooting DNS on a client. Would've saved me the detour.

### 8:10 PM

Joined the domain. Right-click Start > System > Rename this PC (advanced) > Change, selected Domain, typed `lab.local`, authenticated as `LAB\Administrator`.

Got a weird error dialog on the way:

> Changing the Primary Domain DNS name of this computer to "" failed. The name will remain "lab.local". The error was: The specified domain either does not exist or could not be contacted.

Confusing wording, looked like a failure at first glance, but it's actually about the DNS suffix setting specifically, not the domain join itself. The join had already gone through, this error is a known cosmetic/DNS-suffix side effect that shows up sometimes right after a successful join.

Confirmed the real state directly instead of trusting the dialog:

```
(Get-WmiObject Win32_ComputerSystem).Domain
(Get-WmiObject Win32_ComputerSystem).PartOfDomain
```

Came back `lab.local` / `True`. Actually joined.

Restarted, logged in as a domain user to prove it end to end.

<summary><h1>Nov 24th, 2026</h1></summary>

#### Goal: finish Phase A — move the computer into its OU, link a password policy GPO, prove the share permissions

### 7:58 PM

Moved the client computer object out of the default Computers container.

```powershell
Get-ADComputer -Filter * | Select Name, DistinguishedName
Move-ADObject -Identity "CN=LAB01,CN=Computers,DC=lab,DC=local" -TargetPath "OU=Whiterun,OU=Workstations,OU=Skyrim,DC=lab,DC=local"
```

Quick, one command, confirmed it landed with `Get-ADComputer -Filter * -SearchBase`.

### 8:05 PM

Went to create the first GPO in Group Policy Management. Got stuck right-clicking the wrong node, `Domains` is just a category folder, the actual domain object (`lab.local`) is nested underneath it and has to be expanded first. 

<img width="634" height="258" alt="image" src="https://github.com/user-attachments/assets/71a1e64d-a8fc-4696-b23e-1c0b7700e861" />

Right-clicking the real `lab.local` node gave me the option I was looking for: **Create a GPO in this domain, and link it here**.

Named it `Default Domain Password Policy`. Set:

- Minimum password length: 10
- Complexity requirements: Enabled
- Maximum password age: 60 days
- Enforce password history: 5

Got asked about the **Enforced** option on the link. Left it unchecked. Enforced only matters once there's a lower-level GPO or a Block Inheritance setting to override, and I have neither yet. Checking it now would've done nothing, since there's nothing to force past. Good thing to test deliberately later once I have a conflicting GPO at a lower OU.

### 8:13 PM

Ran `gpresult /r` on the client as Aela to confirm the policy applied. Got `N/A` under Applied Group Policy Objects and thought it failed.

It didn't. `gpresult /r` on its own prints USER SETTINGS, and a password policy is a **Computer Configuration** setting, so of course nothing shows there. Reran with the right scope:

```powershell
gpresult /r /scope:computer
```

That showed both `Default Domain Policy` and `Default Domain Password Policy` under Applied Group Policy Objects, and the computer's DN confirmed it as `CN=LAB01,OU=Workstations,OU=Skyrim,DC=lab,DC=local`, so both the move and the GPO link were already working, I was just reading the wrong half of the output.

Lesson: `gpresult /r` without a scope shows USER settings by default, and a GPO that only touches Computer Configuration won't show anything there. Check the right half before assuming something didn't apply.

### 8:17 PM

Logged into the client as `LAB\aela`, opened `\\DC01\Jorrvaskr`. Worked, as expected, she's in GG_Companions, which is nested into DL_Share_Jorrvaskr_RW.

Logged out, logged in as `LAB\esbern`, tried the same path. Access denied, also as expected. Esbern's only in GG_Blades, which has no path into that DL group.

Both outcomes matched the design. This is the actual payoff of the AGDLP work from weeks ago, deny-by-default proven end to end with two real logins on a real joined client, not just `Get-ADGroupMember -Recursive` on the DC.

#### Phase A is done: client joined, moved into Workstations\Whiterun, password policy GPO linked and confirmed, share permissions tested against both an authorized and an unauthorized user with matching results.
